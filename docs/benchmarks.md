# 性能与一致性测试报告

本文档记录 **小众点评 (xzdp-go)** 在本机真实 PostGIS、Redis 和 Kafka 环境下的压测结果与复现方法，原始 JSON 数据保存在 [benchmarks-raw.json](benchmarks-raw.json)。

## 测试环境

- **硬件与系统**：Apple M4、macOS arm64（`darwin/arm64`）
- **运行时与中间件**：Go 1.27.3、PostgreSQL 17.6、PostGIS 3.5.3、Redis 8.8.4（`--appendfsync everysec`）、Apache Kafka 3.9.1
- **测试范围**：本机直接调用服务层连接 Redis、Kafka 与 PostGIS。秒杀吞吐统计的是 Redis Lua 预占加 Kafka 投递的受理阶段；端到端耗时包含买家重复重试、异步写库以及崩溃漏发补发。

## 一、商铺多级缓存与击穿保护

测试同一热门商铺在 3 种场景下的表现：进程内 L1 缓存命中（64 并发 5,000 次）、清空 L1 仅命中 Redis（64 并发 5,000 次）、清空 L1 与 Redis 后 200 个并发请求同时冷读。

| 场景 | 并发 / 请求数 | 吞吐 | P50 / P99 延迟 | 实际回源数据库次数 |
|---|---:|---:|---:|---:|
| L1 进程内 LRU 命中 | 64 / 5,000 | **1,685,890 QPS** | 0.0009 / 0.64 ms | **0** |
| L2 Redis 命中 | 64 / 5,000 | **59,996 QPS** | 0.99 / 4.89 ms | **0** |
| 200 并发同时冷读（防击穿） | 200 / 200 | **139,381 QPS** | 0.83 / 1.25 ms | **1**（`singleflight` 合并） |

## 二、高并发秒杀、Kafka 异步落库与崩溃漏发补发

200 个并发用户同时争抢 100 张秒杀券（混入重复请求校验一人一单），并刻意制造 **10 笔“Redis Lua 已扣库存但模拟 API 崩溃未发往 Kafka”的订单**，验证 Worker 定时对账扫描能否自动找回并全部幂等落库。

| 模式 | 受理吞吐 | 受理 P50 / P99 | 落库订单 | 超卖 / 重复 / 丢单 | 崩溃漏发自动找回 | 剩余待处理 |
|---|---:|---:|---:|---:|---:|---:|
| 单桶（`STOCK_BUCKETS=1`） | **16,152 QPS** | 5.24 / 12.22 ms | **100 / 100** | **0 / 0 / 0** | **10 / 10** | **0** |
| 八桶（`STOCK_BUCKETS=8`） | **10,836 QPS** | 3.73 / 18.44 ms | **100 / 100** | **0 / 0 / 0** | **10 / 10** | **0** |

> 说明：单桶与八桶整轮含重试、消费与补发的端到端完成时间分别为 **274 ms** 和 **5,309 ms**（后者受本轮对账周期触发时序影响），剩余库存均为 0。单实例 Redis 下单桶无需循环跨桶，吞吐更高；多节点或极高热点单券场景可按需开启分桶。注意：漏发补发依赖 Redis 待处理索引仍在，若在 `everysec` 刷盘窗口内 Redis 主机同时断电丢失内存，仍存在极短的丢单窗口。

## 三、PostGIS 附近商铺空间索引检索

向 PostgreSQL 批量写入 10,000 家带经纬度坐标的商铺后，以 20 并发执行 500 次带关键词过滤与 `ST_DWithin` 距离排序的附近搜索。

| 指标 | 实测结果 |
|---|---|
| 商铺数据量 | 10,000 家 |
| 并发 / 请求数 | 20 / 500 |
| 吞吐 | **3,307 QPS** |
| 延迟 P50 / P99 | **4.14 ms / 36.56 ms** |

## 复现命令

启动 PostGIS、Redis 和 Kafka 后，配置 `DATABASE_URL`、`REDIS_URL` 和 `KAFKA_BROKERS` 并运行：

```sh
make bench
```
