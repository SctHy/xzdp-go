# 点评后端迁移 PostgreSQL 的性能实验

当前验收脚本使用课程库的 14 家商铺。文中的万店测量和执行计划归档自旧版本，当前脚本用于小样本功能对照。


本次把商铺、笔记和用户从隔离的 MySQL 复制到 PostgreSQL，沿用同一套 Hertz 找店接口和响应格式，测量用户可见的搜索耗时。对热门榜和交易另测实际使用的数据库操作。这份报告记录切换前的对照。当前默认部署和同库优化结果见[PostgreSQL 主库迁移](postgres-migration.md)。

## 从其他点评项目学到的设计

| 项目 | 源码里的做法 | 在这里如何验证或取舍 |
|---|---|---|
| Beli 餐厅点评 | 经纬度使用 geography(Point,4326)，加 GiST 空间索引。餐厅名另建 trigram GIN，城市和评分还有组合索引。 | 迁移时从原 x/y 生成地理点，用 ST_DWithin 先筛半径，再按球面距离、ID 排序。当前“咖啡馆”是字面子串查询，本轮没有引入模糊搜索或文字 GIN。 [餐厅迁移 SQL](https://github.com/tor-iv/beli-app/blob/1e712b2816f3e8d55afcc2b1bbbc5b67dea9816f/supabase/migrations/00002_restaurants.sql) |
| Restaurant Finder | GeoDjango 把餐厅位置存成 PointField，查询先在指定半径筛餐厅，再筛菜品并排序。 | 保留先筛候选再分页的语义。是否实际使用空间索引由 EXPLAIN ANALYZE 核验。 [模型](https://github.com/manishapb/restaurant-finder/blob/363ede3934a3364657e47a7a9fe7bd90406d880a/resto/models.py) · [查询](https://github.com/manishapb/restaurant-finder/blob/363ede3934a3364657e47a7a9fe7bd90406d880a/resto/views.py) |
| 黑马点评 hmdp-ai-agent | PostgreSQL 检查点存会话增量，并定期保存完整快照以限制回放长度。 | 适用于未来的多轮探店助手。项目里的这一实现无法说明 PostgreSQL 对商铺搜索或秒杀的影响，本轮交易结果来自本地对照。 [检查点实现](https://github.com/yeffky/hmdp-ai-agent/blob/29025a5b134d94a98f29ecf05543f9b16afbbbda/hm-dianping/src/main/java/com/hmdp/agent/graph/checkpoint/DeltaPostgresSaver.java) |

## 实验口径

- 同一台 arm64 Colima 虚拟机。MySQL 8.4.13 和 PostgreSQL 17.6 / PostGIS 3.5.3 各限 2 CPU、512 MiB 内存，InnoDB 缓冲池和 PG shared_buffers 均为 96 MiB。MySQL 提交刷盘为 1 且 sync_binlog=1，PG 的 fsync 和 synchronous_commit 都开启。都是本机单实例。
- 从项目种子 SQL 建立独立 MySQL，补入分布在同一城市约 0.5° × 0.5° 范围的 24,000 家商铺、12,000 篇笔记及一篇赞数为 NULL 的笔记。用 COPY 从 MySQL 逐行迁入 PG。按主键顺序对三张表的全部源字段做 SHA-256 对照，包括 NULL、中文、坐标和时间戳。两边均有 24,014 家店、12,005 篇笔记、1,005 个种子用户。
- 每个场景先预热 24 次，随后每库 8 并发，每轮 120 次，交替运行顺序，每个全新环境做 4 轮，共重建 3 次环境，每个对照项有 12 轮正式样本。表中 P50、P95 与吞吐量均取各轮指标的中位数。QPS 是这个并发度下的完成速率。P95 表示该轮 95% 的请求在这一时间内完成。
- 找店走本机 HTTP，包含 Hertz 绑定、数据库往返、JSON 编解码和结果比对，使用同一 Go 客户端。两端只加载找店路由。榜单重建、按编号取回笔记、竞争余位、订单持久化测 Go 客户端到数据库的耗时。Redis 命中、Kafka 排队、鉴权、跨机网络均在计时范围之外。
- 搜索轮换 35 个中心点。无关键词查 1 公里内前 10 家，有关键词则指定分类查 2.6 公里范围内的“咖啡馆”，交替取前两页。逐请求比对条数、顺序、ID、名称、分类和距离，允许距离误差 2 毫米。另测同址的 ID 顺序、半径边界内外各 1 厘米、字面百分号及带重音的名称。
- 基线沿用当前 MySQL 的分类索引，PG 同样只有分类与主键索引。优化组给 MySQL 加 R-tree，用外接矩形缩小候选后再计算精确距离；PG 加 GiST，用 ST_DWithin 做候选过滤。两库都为榜单加 (liked DESC, id DESC) 索引。PG 明确指定 NULLS LAST，保证没有点赞数的笔记与 MySQL 的排序一致。
- 余位测试让 120 个操作竞争 90 个名额，统计含 30 次正常拒绝。订单测试让 120 个不同买家成交同一张券，在一笔事务内写幂等回执、订单、扣库存、写通知，设置等价的唯一索引和普通索引。测试完成后重放已成功的订单，并提交一个库存耗尽的新订单，逐表检查回执、订单、通知均为 120 条，库存为零。订单测试使用独立表，模拟 Kafka 消费者的持久化事务。

## 本地结果

P95 越低越好，最后一列表示 PG 相对同组 MySQL 的耗时变化。

| 索引组 | 场景 | MySQL P50 / P95 ms | PG P50 / P95 ms | MySQL / PG QPS | PG 的 P95 变化 |
|---|---|---:|---:|---:|---:|
| 基线 | 命中榜单后取 10 篇详情 | 0.82 / 0.99 | 0.87 / 1.07 | 9,508 / 8,855 | +8.2% |
| 基线 | 分类 + 中文关键词 HTTP | 8.28 / 50.75 | 3.03 / 4.86 | 591 / 2,440 | -90.4% |
| 基线 | 1 公里附近店铺 HTTP | 25.77 / 75.40 | 26.84 / 76.25 | 189 / 183 | +1.1% |
| 基线 | 订单落库事务 | 8.06 / 9.75 | 5.39 / 12.97 | 960 / 1,227 | +33.0% |
| 基线 | 重建热门前 100 名 | 4.36 / 44.85 | 2.95 / 5.05 | 1,098 / 2,529 | -88.7% |
| 基线 | 条件扣 1 个余位 | 2.76 / 3.30 | 0.73 / 2.13 | 3,495 / 8,944 | -35.4% |
| 已优化 | 分类 + 中文关键词 HTTP | 1.57 / 2.13 | 1.67 / 2.61 | 4,898 / 4,461 | +22.6% |
| 已优化 | 1 公里附近店铺 HTTP | 1.10 / 1.33 | 1.51 / 2.09 | 7,033 / 5,091 | +56.5% |
| 已优化 | 重建热门前 100 名 | 0.61 / 0.85 | 0.53 / 0.79 | 12,423 / 14,152 | -7.2% |

1. 现有 MySQL 附近查店 P95 为 75.40 ms，PG 加空间索引后为 2.09 ms，降低约 97.2%。给 MySQL 加空间索引后为 1.33 ms。普通附近查询的大部分收益在原数据库也能得到。关键词加分类的场景中，PG 基线已有明显收益，但两库都加空间索引后 MySQL 同样领先。
2. 在同一采样坐标，PG 无空间索引时扫描 24,014 家店。使用 GiST 后先命中 45 个候选，再用精确半径筛出 28 家并取前 10。MySQL 的矩形筛选也使用了空间索引。榜单复合索引让 PG 从按全表排序变成按索引顺序读出 100 篇。命中 Redis 后的详情 SQL 仍接近 1 ms，两条读路径的收益差别很大。[实际执行计划](performance/postgres-plans.txt)
3. PG 条件扣余位的 P95 降低 35.4%。完整落单事务吞吐从每秒 960 笔增至 1,227 笔，增幅约 28%，但 P95 从 9.75 ms 增至 12.97 ms，慢了 33%。三个独立环境中 PG 的事务 P95 都比同批 MySQL 高。对有延迟承诺的下单链路，应先拿真实并发和支付、取消混合负载复验。

如果目标是加快当前附近搜索，优先交付 MySQL 空间索引就能验证用户收益。如果后续需要门店配送范围、多边形相交等空间能力，适合把 PostGIS 找店做成第一条 PG 读路径，使用真实请求做双读比对，并单独评估交易切换。

## 迁移时应保留的语义

- 当前 MySQL 对 SRID 0 的球面距离使用 6,370,986 米半径。PG 实验对 WGS84 球面距离换算后才用于返回值和半径边界。MySQL 的 LOCATE 在现有列排序规则下能匹配 `café` 与 `CAFÉ`，输入 `cafe` 却不能匹配 `Café`。实验用大小写折叠并保留重音。真实店名中的其他文字和排序规则仍需在切流前抽样比对。
- 榜单前 100 名由后台刷新。排序索引加速重建，用户翻阅已缓存的首页仍需按主键取笔记详情。这两个耗时应分别观察。
- PG 用针对回执主键的 ON CONFLICT DO NOTHING 处理重复投递。订单、库存和通知一起提交，失败一起回滚。正式迁写还要检查无符号 ID 的范围，在导入后校准自增序列，并改造占位符、LastInsertId、时间函数、迁移锁及 Redis GEO 脏数据触发器，验证付款、核销、关单和候补的端到端恢复。
- 本轮能支持的是热缓存、小型单库的迁移决策。切生产前还需要真实商铺密度、长尾关键词、线上读写比例，以及持续写入时的 WAL、复制延迟、autovacuum 与故障恢复数据。

## 复验

在仓库根目录运行，需要 Docker Compose、Go 和 Python 3。脚本创建单独的 Compose 项目，端口只绑定本机并自动分配，退出时回收实验容器和数据卷。

```sh
sh script/pgbench/run.sh > pgbench.log 2>&1
python3 script/pgbench/summary.py pgbench.log
```

多次独立运行时给汇总脚本传入多个日志文件，可用 `--csv samples.csv` 导出每一轮。SQL 执行计划与逐表校验摘要在运行日志中。[实验入口](../script/pgbench/run.sh) · [逐轮样本](performance/postgres-samples.csv)
